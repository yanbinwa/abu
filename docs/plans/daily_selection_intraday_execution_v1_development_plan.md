## 1. 计划目的

本计划把设计文档中的 `hybrid_intraday_entry_v1` 拆成可以逐阶段开发、测试、Review 和准入的工作项。

v1 的目标不是证明“分钟数据能够提高收益”，而是建立一条可复现的分钟级买入执行链路：

1. 继续使用日线数据选股、打分、风控和生成目标仓位；
2. 把次日买入从“开盘价一次性理想成交”改成分钟数据驱动的、可解释的订单状态机；
3. 保持卖出、组合记账和日线策略口径不变；
4. 支持同一批已批准订单在 D0、M1、M2 三种执行方式下做配对比较；
5. 支持分钟行情采集、历史回放和实时影子运行；
6. 在接入真实券商网关前，用数据和运行证据判断分钟执行方案是否值得继续。

本计划不承诺收益提升。完成标准是系统行为正确、没有未来数据泄漏、结果可以审计，且对现有日线执行路径保持兼容。

## 2. 开发原则

### 2.1 保持 D0 为默认路径

- 未显式指定分钟执行策略时，现有回测与纸上交易继续使用 D0。
- M1、M2 必须通过新配置显式开启。
- 在 D0 等价性测试通过前，不允许把新执行器接入现有运行入口。

### 2.2 一次只改变执行变量

- 第一轮配对实验固定选股结果、风控审批结果、目标股数和卖出路径。
- D0、M1、M2 只改变买入执行价格与能否成交。
- 不在同一开发周期调整 VCP/Alpha158 特征、排名、仓位、止损或止盈参数。

### 2.3 时间因果性优先

- 决策只能访问 `available_at <= decision_time` 的数据。
- 分钟 bar 必须使用已完成 bar；不得用尚未结束 bar 的高、低、收、量。
- 所有实时事件同时保存市场时间、请求时间、接收时间和可用时间。
- 对输入中的未来字段做污染测试，证明策略输出不受其影响。

### 2.4 数据异常默认关闭交易

- 无数据、陈旧数据、时间戳语义未知、字段异常或源切换不一致时，不生成成交。
- “HTTP 请求成功”和“获得可交易的新鲜数据”是两个独立状态。
- 降级与切源必须产生结构化原因码和审计记录。

### 2.5 原始事件追加写入

- 原始响应、标准化 bar、订单事件和成交事件均采用追加写入。
- 数据修订通过新版本表达，不覆盖旧记录。
- 回放必须能指定数据快照和延迟模型，得到确定性结果。

### 2.6 保护现有工作区与纸上交易状态

- 当前工作区存在与本计划并行的未提交修改；实施前先确认所有权和冲突，不覆盖或顺带提交无关改动。
- `ABuVCPPaperTrading` 的实现哈希包含共享策略/执行代码。修改共享执行器后，现有状态可能被拒绝加载。
- 开发完成不等于允许部署到当前纸上交易实例；状态版本、迁移方案和回滚方案必须单独 Review。

## 3. 本期范围

### 3.1 包含

- 分钟行情时间语义和健康状态；
- 标准化 `MinuteBarEvent`；
- 分钟数据追加式存储、读取、审计与回放；
- M1、M2 买入执行策略；
- 订单指令、订单事件和成交事件扩展；
- D0 等价性保护；
- 配对执行回测；
- 独立组合回测；
- 实时影子运行；
- 延迟统计、失败原因统计和准入报告。

### 3.2 不包含

- 真实券商委托、撤单、成交回报或资金查询；
- tick 级撮合和盘口队列建模；
- 分钟级卖出、止损、止盈；
- 盘中重新选股或改变目标仓位；
- 使用分钟数据训练新的选股模型；
- 多标的智能路由；
- 对数据源 SLA、合规权利或长期稳定性的隐含保证。

- 相同事件重复写入不会产生逻辑重复；
- 同一 bar 的修订可以按 `as_of` 得到不同版本；
- 写入中断后不暴露不完整分区；
- 同一 manifest 回放两次事件序列一致；
- provider 切换前后的字段语义可追踪；
- 午休期间不会被误判为缺失 bar；
- 缺少 `volume_shares` 时 M2 禁止执行；缺少允许为空的 `amount_raw` 时仅记录质量码；
- 采集器重启后不会跳过已完成但未落盘的事件，也不会重复发布逻辑事件。

### 9.4 两层验收门禁

软件门禁：

- 存储、读取、审计、重启和幂等测试通过；
- 至少完成一个完整交易日的人工检查；
- 可进入 M4/M5 的固定延迟开发。

经验数据门禁：

- 累积至少 10 个有效交易日；
- 各 provider 的 p50、p95、p99 延迟和失败率可计算；
- 才允许冻结经验延迟分布和生产建议轮询参数。

### 9.5 完成条件

- 软件门禁通过；
- 数据目录、schema 和 manifest 版本已冻结；
- 审计报告能定位到具体 symbol、bar 和原因码；

## 11. MS4：M1/M2 订单状态机与执行规则

### 11.1 目标

### 11.2 开发任务

- [ ] M4-T04 实现 `IntradayTradability`，只接受决策时刻可见的数据。
- [ ] M4-T05 实现 M1：在指定完整 bar 上做一次成交判断。
- [ ] M4-T06 实现 M2：在窗口内逐 bar 寻找首个满足价格、交易状态和流动性约束的候选。
- [ ] M4-T07 实现全成或不成；无法全量成交则继续等待或到期，不产生部分成交。
- [ ] M4-T08 实现 M2 最大参与率检查，默认候选值为 bar 成交量的 5%。

- [ ] M4-T12 支持保守涨停主结果和乐观敏感性分析，但不得混为同一实验。

### 11.3 状态机约束

```text
CREATED -> ACTIVE -> CANDIDATE -> FILLED
                    |
                    -> ACTIVE     # 候选不满足全量成交，继续等待

CREATED/ACTIVE/CANDIDATE -> CANCELLED
ACTIVE/CANDIDATE         -> EXPIRED
```

- 终态为 `FILLED`、`CANCELLED`、`EXPIRED`；
- 终态之后不得再接收会改变资金或持仓的事件；
- 一个指令最多生成一个买入成交；
- 每个状态变化都必须引用输入事件和规则版本。

### 11.4 测试矩阵

| 场景 | M1 预期 | M2 预期 |
|---|---|---|
| 触发 bar 正常且足量 | 成交 | 成交 |
| 触发 bar 无量，后续恢复 | 过期/拒绝 | 后续首个合格 bar 成交 |
| 一直停牌 | 过期 | 过期 |
| 涨停封板 | 保守不可成交 | 窗口内持续检查，仍封板则过期 |
| 候选 bar 容量不足 | 不成交 | 继续等待 |
| 数据晚于决策时间到达 | 不可用 | 只能在到达后的下一次决策中使用 |
| bar 尚未结束 | 不可用 | 不可用 |
| 公司行动异常 | 取消 | 取消 |
| 资金在等待中被其他订单占用 | 不允许 | 不允许 |
| 重复事件 | 不重复成交 | 不重复成交 |

另外加入“未来污染”测试：故意修改当天收盘价、最高价、最低价和全日成交量，若这些字段在决策时刻不可用，M1/M2 输出必须保持不变。

容量测试还必须故意修改候选成交 bar 的最终成交量；此前已经做出的成交决定必须保持不变。

### 11.5 完成条件

- `paper_state_version`。

版本改变必须记录兼容性。破坏性变化只新增读兼容或迁移工具，不静默重写旧产物。

### 17.2 运行身份

`run_id` 至少由以下信息决定：

- 代码 commit；
- `dirty` 标志、源码快照 manifest 和 `source_snapshot_hash`；
- 配置内容哈希；
- 数据 manifest 哈希；
- 策略和执行规则版本；
- 延迟模型版本；
- 实验类型与创建时间。

创建时间不参与确定性业务结果，只用于区分运行目录。

## 19. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| provider 时间戳语义错误 | 产生隐蔽未来泄漏 | provider 逐一契约测试，未知语义失败关闭 |
| 历史分钟窗口短 | 统计结论不稳定 | 明确样本范围，分层报告，不外推长期收益 |
| 实时延迟与历史回放不一致 | 回测过于乐观 | 真实采集延迟，固定/经验延迟敏感性 |
| 成交量或成交额缺失 | M2 无法判断容量 | 降级为不可执行或单独规则，不推测 |
| 共享执行器重构破坏纸上恢复 | 当前任务中断 | 新状态根、版本迁移、备份与恢复演练 |
| 未提交代码与本计划冲突 | 覆盖用户工作或基线不清 | M0 归属清单，独立分支/工作树，按文件提交 |
| 组合路径分叉难以归因 | 误解收益变化 | 先做配对回放，再做独立账本和首个分叉报告 |
| 事后调参 | 研究结论失真 | 预注册实验，保留所有运行，不覆盖结果 |
| provider 许可或接口变化 | 生产不可持续 | 保留 provider 抽象、原始记录和替换能力 |
| 过早引入盘中卖出 | 同时改变多个变量 | 设 M8 独立门禁，v1 不实现 |

## 20. 建议的实施节奏

在一名主要开发者、Review 及时且不含外部等待的前提下，可按以下节奏估算；这是工作量级别，不是承诺日期。

| 周期 | 工作 | 退出结果 |
|---|---|---|
| 第 1 周 | M0、M1 | 契约冻结，时间语义正确 |
| 第 2 周 | M2 软件部分、启动采集 | 数据可追加、审计、开始积累 |
| 第 3 周 | M3 | D0 等价，纸上状态方案通过 |
| 第 4–5 周 | M4 | M1/M2 状态机完成 |
| 第 6 周 | M5 | 首轮配对回放 |
| 第 7 周 | M6 | VCP 独立组合回测 |
| 第 2–7 周并行运行 | M7 数据采集与影子观察 | 达到 10/20 日门槛 |
| 数据门槛达到后 | M8 | 准入结论 |

若遇非交易日、provider 故障或规则修改，10 日和 20 日门槛按“有效交易日”计算，不能用自然日替代。

## 22. 总体验收标准

只有以下条件全部满足，开发计划才算完成：

- D0 仍是默认且通过等价性验证；
- 分钟行情包含完整时间语义、健康状态和版本信息；
- 原始和标准化数据可追加存储、审计和按版本回放；
- M1/M2 不访问决策时刻之后的数据；
- 订单状态机幂等，资金预留和释放正确；
- 配对回放和独立组合回测均可复现；
- 实时影子运行至少覆盖 20 个有效交易日；
- 故障恢复不会重复成交或静默猜测成交；
- 现有纸上交易状态有明确迁移、隔离和回滚路径；
- 全部 Review 文档完成；
- M8 给出明确的 `ACCEPT_V1`、`ACCEPT_DATA_ONLY`、`REVISE_AND_REPEAT` 或 `REJECT` 结论。
